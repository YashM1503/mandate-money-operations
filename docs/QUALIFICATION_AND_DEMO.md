GIDE is a development tool. Its CLI supports working beside other editors and cloud models. Thus a technically sound workflow is to use ChatGPT, Claude or Cursor for separate files, then use GIDE for a substantive implementation or testing segment in the same repository. Moving files, opening an already finished repo, or pushing through a terminal alone does not demonstrate meaningful use. Nothing in the supplied messages expressly requires exclusive GIDE use. Eligibility is the organizer's decision, not something this repository can certify.

A GitHub push is ordinary source control; it does not need to pass through PRISM. PRISM observes actual agent execution. GIDE helps build and test code. Deployment can remain local or use a cloud service; these choices are independent.

## Differentiate against the described transaction-risk agent

The competitor post is an idea description, not a review of its finished product. It proposes flags, explanations, human escalation and audit logs. Assume they can implement these well; their stated AML background may make broad compliance scoring a poor contest for this team.

Mandate should lead with one narrower failure: the agent updates a supplier master from an unverified message, then cites that matching master as independent authorization. Ordinary confidence and logging do not solve this origin problem. Mandate carries source ancestry into a payment-intent decision and requires an independent verifier before approval. Changed evidence, amount, beneficiary or cash context invalidates the relevant authorization, and the effect boundary admits only one exact simulated payment.

Suggested opening: “Your agent found a matching bank account. The problem is that your agent put it there. Mandate checks whether the evidence is independent before money can move.”

Do not claim first-to-market, patented novelty, guaranteed fraud prevention, network certification or a 9/10 objectively measured differentiation score. The current differentiation case is strong if judges see an enforced failed execution and a legitimate successful execution. A generic dashboard with an extra source-count metric is substantially weaker.

## Three minute demo

1. 0:00–0:25. Introduce Yari, a synthetic retailer owner. Open Atlas's valid $47,850 invoice with a bank change from 4831 to 9924. The invoice amount alone is not the risk.
2. 0:25–1:00. Inspect request → extraction → agent-updated master. Explain one source root, not three independent confirmations. Show that the server will not approve or release it. Present a PRISM trace from the real investigator, when available.
3. 1:00–1:40. In an analyst session record independent verification through the established contact. In a separate controller session review and approve the exact payment; release once. Show the ledger and remaining cash. The demo attestation is synthetic; do not pretend a real bank validation occurred.
4. 1:40–2:10. Use a fresh fixture or a different case to demonstrate changed intent invalidating approval, and an execution retry returning the same ledger ID. A short recorded backup can show these if role switching is slow.
5. 2:10–2:40. Show the same evaluation set before and after the control, including legitimate cases. Open PRISM's bad run, improvement and rerun. Clearly distinguish constructed local tests from actual model runs.
6. 2:40–3:00. Explain deployment: authenticated API, deterministic controls, synthetic payment adapter; next customer work is ERP integration and trusted beneficiary attestation. Show actual GIDE development evidence.

Prepare two authenticated browser sessions before presenting, plus a local server and a short video backup. Demo data should start fresh; releasing Atlas first deliberately leaves only $2,150 available above commitments and reserve. Do not then expect Northstar's $8,240 payment to pass cash policy. Use a separate fresh database to show Northstar's successful routine path.

## Four hour scope

Minutes 0–20: confirm rules and problem statement, pin starting commit, connect GIDE and PRISM, run the first real traced investigation. Minutes 20–110: complete any required sponsor/provider adapter and fix core failures; UI and tests can proceed with separate file owners. Minutes 110–165: verify attack and legitimate paths with the same scenario IDs. Minutes 165–195: use PRISM findings to make one substantive improvement through GIDE and rerun. Minutes 195–220: smoke-test local and chosen hosted environment, save evidence and video. Minutes 220–240: freeze code, finish README/demo link and submit before lock.

Avoid new OCR pipelines, real payments, broad AML claims, a multi-agent voting committee, voice verification, and unrelated ticketing integrations in this time box. Tavily can support a later research-only contextual source panel, but retrieved pages must never authorize a bank change. ElevenLabs can narrate a demo if useful; voice identity does not independently verify a beneficiary.
